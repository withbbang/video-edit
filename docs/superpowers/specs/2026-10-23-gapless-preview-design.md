# 앱 미리보기를 완성 mp4 처럼 이어서 재생하기 — 설계

2026-10-23

## 왜

앱의 미리보기는 컷을 적용하지 않은 원본 사본(`preview.mp4`)을 재생하다가 잘린 구간 시작에 닿으면
`currentTime` 을 그 구간 끝으로 옮긴다 (`app/ui/app.js` 의 `player.tick`). 사용자는 이걸 "말하다가 툭 끊기고
찰나의 순간 멈췄다가 이어지며, 문장 앞뒤가 잘린다"고 느꼈다. 같은 설정으로 렌더한 완성 mp4
(`~/Movies/youtube-edit/3_clean.mp4`)는 맥·윈도우 기본 플레이어에서 자연스럽다고 했다.

측정 (3.mp4 앞 40초, 이음새 15곳, `requestVideoFrameCallback` 으로 실제 그린 프레임 간격):

- 맥 WKWebView(앱과 같은 엔진): 지금 방식은 이음새마다 0.35~0.38초 멈춤. 재생기 둘을 번갈아 쓰는 방식도
  멈춰 둔 재생기를 다시 재생할 때 같은 만큼 걸려서 효과 없음 (시도 후 되돌림).
- Chromium(윈도우 WebView2 와 같은 엔진): 지금 방식은 멈춤이 거의 없지만 소리 경계가 거칠다.

버린 시험판(scratchpad, 저장소 밖)으로 MediaSource 에 남길 구간만 이어 붙여 넣어 보았다:

| 시험 | 결과 |
|---|---|
| A 영상 기준 프레임 0.4초 간격 + appendWindow 로 자르기 | 구간 시작이 다음 기준 프레임까지 버려져 영상에 구멍 → 못 씀 |
| B 모든 프레임이 기준 프레임 + 원본 소리를 appendWindow 로 자르기 | 끊김 없이 재생되지만 사용자는 "여전히 부자연스럽고 문장 앞뒤가 잘린다" |
| D B + 말 앞뒤 여유 더 남기기 | (사용자가 E 와 비교 후 E 선택) |
| **E 영상은 B, 소리는 완성 mp4 의 소리를 그대로 이어서** | **맥·윈도우 모두 "자연스럽다"** |

B 와 E 의 차이는 소리뿐이다. 브라우저는 AAC 소리를 1024샘플(21ms) 단위로만 자르고 각 구간 앞 조각을 버리므로
(WKWebView 소리 버퍼가 0.015초에서 시작), 이음새마다 말머리·말꼬리가 깎였다. 파이프라인 `cut_audio` 는
샘플 단위로 자르고 이음새에 3ms 페이드를 넣는다. 그래서 **소리는 파이프라인이 잘라 만든 것을 그대로 쓰고,
영상만 브라우저에서 이어 붙인다**.

## 목표

- 앱 미리보기를 재생하면 렌더할 완성 mp4 와 같은 소리, 같은 컷으로 이음새에서 멈춤 없이 이어진다. 맥(WKWebView)과
  윈도우(WebView2) 둘 다.
- 잘린 곳을 되살리거나(`set_restored`), 타임라인에서 직접 자르거나 되살리거나(range ops), 실행 취소·다시 실행하면
  미리보기도 그 컷으로 바뀐다.
- 화면의 모든 시간 표시·조작(타임라인 재생 위치, 영상 위 자막, 구간 선택, `지금 위치로`, 잘린 곳 들어보기)은
  지금처럼 원본 기준 시간으로 동작한다.

## 하지 않는 것

- 완성 mp4 렌더 방식, 컷 판정, CLI 동작은 바꾸지 않는다.
- 미리보기에서 음량·화질을 완성본과 똑같이 맞추지는 않는다 (소리는 같은 오디오 소스와 같은 자르기, 영상은 저해상도).
- 잘린 구간 안의 소리를 미리보기로 들려주는 기능은 새로 만들지 않는다 (지금도 없다).

## 실패로 보는 것 (돌아가도 안 되는 것)

- 이음새에서 멈칫하거나 말머리·말꼬리가 깎이는 게 남아 있다. 시험판 E 보다 나빠지면 실패다.
- 컷을 바꿨는데 미리보기의 소리와 영상이 서로 다른 컷을 쓴다 (입 모양과 소리가 어긋남).
- 긴 영상(1시간)에서 미리보기를 못 만들거나, 재생 중에 메모리·버퍼 한도로 멈춘다.
- MediaSource 가 실패하면 미리보기가 아예 안 나온다 (예전 방식으로라도 나와야 한다).

## 제약

- 맥 WKWebView, 윈도우 WebView2(Edge). 둘 다 MediaSource 로 H.264 + AAC(fMP4)를 받는다.
- SourceBuffer 한도: Chromium 기본은 영상 약 150MB, 소리 약 12MB다. 전체를 한 번에 넣을 수 없으므로
  재생 위치 앞뒤 일부만 넣고 지나간 부분은 지운다.
- 미리보기 파일은 사용자 데이터 폴더(`jobs/<id>/`)에 둔다. 앱 설치 폴더에는 쓰지 않는다.
- 미리보기 서버(`app/window.py` `serve_previews`)는 이미 Range 요청을 지원한다.
- 화면 문구는 데스크톱 앱 스펙(`docs/superpowers/specs/2026-10-22-desktop-app-design.md` 3장)과 맞춘다.
  새 문구가 필요하면 그 스펙에도 추가한다.
- 테스트: 파이프라인·API 는 pytest. CI 의 pytest 단계엔 ffmpeg 가 없다. JS 테스트 체계는 없다.

## 설계

### 1. 영상: 모든 프레임이 기준 프레임인 조각 미리보기

- `make_preview_video` 가 만드는 소리 없는 사본을 **fragmented MP4, 모든 프레임이 기준 프레임(`-g 1`), B 프레임 없음**으로
  바꾼다. 조각(moof+mdat)은 약 0.5초 단위.
- 크기·속도 측정 (60초 원본, libx264 veryfast, `-g 1`):

  | 설정 | 크기 | 인코딩 |
  |---|---|---|
  | 1280px crf 26 | 81MB/분 | 6.8초 |
  | 1280px crf 30 | 54MB/분 | 6.1초 |
  | **960px crf 30** | **35MB/분** (5분 175MB, 1시간 2.1GB) | **3.9초** |
  | 854px crf 32 | 24MB/분 | 3.5초 |
  | VideoToolbox 960px 4M | 30MB/분 | 6.0초 |

  **내 판단**: 긴 변 960px, libx264 crf 30 (VideoToolbox 의 `-g 1` 은 더 느리고 품질 조절이 비트레이트뿐). 화면 크기
  미리보기용으로 충분하다고 본다. 지금 미리보기(1280px, 0.4초 간격)는 5분에 113MB였다.
- 파이썬이 조각 목록을 JSON 으로 남긴다: `preview_video.index.json` = `{timescale, init: [0, 끝 바이트], frags: [[시작초, 시작 바이트, 끝 바이트], …]}`.
  상자(`moov`, `moof`>`traf`>`tfdt`)를 읽어 만든다. 브라우저는 이 목록으로 필요한 바이트 범위만 Range 로 받는다.
- 캐시 키(`preview_video.meta.json` 의 `v`)를 올려 기존 작업은 처음 열 때 한 번 다시 만든다.
- 영상 원본 프레임 간격과 미리보기 프레임 간격이 다를 수 있다(원본 30.005fps → 미리보기 30fps). 시험판에서
  `appendWindowEnd` 를 구간 끝에 딱 맞추면 끝 프레임이 버려져 1프레임 빈틈이 생기고 재생이 멈췄다. **영상은
  appendWindowEnd 를 1프레임 늘리고 다음 구간이 겹친 프레임을 덮어쓰게 한다** (시험판에서 해결 확인).

### 2. 소리: 파이프라인이 잘라 만든 미리보기 소리

- 새 숨은 옵션: `pipeline.py <src> --preview-cut-audio <out.m4a> --apply-cuts <cuts.json> --work-root … --out …` (`--denoise-level` 등
  미리보기 소리 옵션 포함). 미리보기에 쓰는 소리(지금 `make_preview` 의 `clean_wav`: 기본 `clean.wav`, `--denoise-level` 이면
  그 세기의 렌더 오디오)를 `keep_segments` + `cut_audio`(렌더와 같은 3ms 페이드)로 자르고, AAC 128k fMP4 로 인코딩하고,
  같은 형식의 `index.json` 을 함께 쓴다. 전사·판정은 하지 않는다.
- 측정: 168초 소리 AAC 인코딩 2.35초(기본), `-aac_coder fast` 0.97초, macOS `aac_at` 1.26초. **내 판단**: `-aac_coder fast`
  (두 OS 공통). 1시간 원본(결과 약 40분)이면 약 15초다.
- 앱(`api.py`)은 미리보기에 쓰는 컷(지금 `get_result` 가 만드는 `cur` — 되살린 곳·range ops 반영)이 바뀔 때마다
  이 명령을 백그라운드로 돌린다. 결과 파일 이름에 컷 목록의 해시를 넣어(`preview_audio.<hash>.m4a`) 같은 컷이면 다시 만들지
  않는다. 오래된 파일은 최근 몇 개만 남기고 지운다. `get_result` 는 지금 컷에 맞는 소리가 있으면 그 URL 과 index URL,
  남길 구간 목록(원본 초)을 함께 준다. 아직 만드는 중이면 그 사실을 알려 준다.
- 분석(`--review --preview`)이 끝날 때 판정된 컷으로 한 번 만들어 둔다.

### 3. 재생기: MediaSource 로 이어 붙이기

- `<video>` 하나에 MediaSource 를 붙이고 영상·소리 SourceBuffer 를 하나씩 만든다. 재생기의 시간은 **결과 기준 시간**이다.
- 남길 구간 목록 `keeps = [[s, e], …]`(원본 초)에서 결과 시간 o 를 누적해 원본↔결과 시간 변환 함수를 만든다. 잘린 구간 안의
  원본 시간은 그 구간 끝(다음 남길 구간 시작)으로 보낸다.
- 영상: 남길 구간마다 `timestampOffset = o − s`, `appendWindowStart = o`, `appendWindowEnd = o + (e − s) + 1프레임` 으로 그 구간에
  걸친 조각만 넣는다. 소리: 이미 잘린 소리라 결과 시간 그대로, 자르지 않고 넣는다.
- 버퍼 한도 때문에 재생 위치 기준 뒤 약 10초~앞 약 60초만 넣고 지나간 것은 `remove` 한다 (내 판단, 조정 가능).
  `QuotaExceededError` 가 나면 앞쪽 범위를 줄여 다시 시도한다.
- 화면의 원본 시간 사용처는 모두 변환을 거친다: 타임라인 재생 위치(`drawHead`), 영상 위 자막(`drawSub`),
  `seek`, `clip`(앞뒤 2초 들어보기: 원본 `start − 2` 부터 `end + 2` 까지를 결과 시간으로 바꿔 재생 후 멈춤),
  `지금 위치로`(`player.video.currentTime` 을 쓰는 곳 — 결과→원본으로 바꿔 돌려준다), 재생 중 자막 수정 막기.
- **멈춘 상태에서 잘린 구간 안 보기는 지금처럼 유지한다 (사용자 결정)**. 지금은 원본 타임라인을 재생하므로 멈춘 채
  타임라인의 잘린 구간 안을 누르거나 구간 선택 손잡이(`player.seek(S.range[which])`)를 끌면 그 자리 화면이 보이고, 재생하면
  잘린 구간 끝으로 건너뛴다. 새 방식에서도 멈춘 상태에서 잘린 구간 안으로 옮기면 조각 영상 파일을 원본 시간 그대로 여는
  `<video muted>`(실패 처리의 예전 방식 재생기와 같은 요소를 써도 됨)를 MediaSource 재생기 자리에 보여 주고, 재생을 누르면
  MediaSource 재생기로 돌아가 그 잘린 구간 끝(결과 시간)부터 재생한다. 남길 구간 안으로 옮기면 MediaSource 재생기를 쓴다.
- **브라우저 기본 컨트롤은 그대로 둔다 (사용자 결정)**. 기본 컨트롤의 시간·길이·탐색 막대는 결과 영상 기준(완성 mp4 와 같음)이고,
  그 아래 앱 타임라인은 원본 기준이다. 기본 컨트롤로 탐색하면 결과 시간이므로 변환 없이 그대로 재생한다.
- 컷이 바뀌면: 새 소리가 준비될 때까지 지금 미리보기를 그대로 재생하고, 준비되면 원본 기준 지금 위치를 기억해
  MediaSource 를 새로 만들어 같은 원본 위치(잘렸으면 그 끝)에서 이어 재생한다. 준비 중엔 재생기 근처에 짧은 안내를 보인다.
- 실패 처리: `MediaSource` 가 없거나, `isTypeSupported` 가 거짓이거나, append 오류·소리 준비 실패가 나면 지금 방식
  (원본 타임라인 + 건너뛰기)으로 돌아간다. **내 판단 (디스크를 두 배로 쓰지 않게)**: 영상+소리를 합친 `preview.mp4` 사본은
  더 만들지 않는다. 대신 전체 길이 소리 `preview_audio_full.m4a`(1시간 약 60MB)를 두고, 예전 방식은 조각 영상 파일을
  `<video muted>` 로 그냥 재생(fMP4 는 MediaSource 없이도 재생된다)하면서 `<audio>` 를 함께 틀고, 건너뛸 때 둘의
  `currentTime` 을 같이 옮긴다. 드문 경로라 싱크는 지금 수준이면 된다. 기존 작업의 옛 `preview.mp4` 는 새 미리보기를
  만들 때 지운다.
- 영상이 없는 입력(오디오 파일): **내 판단**: MediaSource 없이 잘린 소리 m4a 를 `<audio>`(지금처럼 `<video>` 요소여도 됨)로
  그냥 재생한다. 시간 변환은 같다.

### 시험판 E 재현 정보

시험판은 저장소 밖 scratchpad 에 있다 (`spike/index.html`). 결과를 좌우한 세부:

- 영상: `ffmpeg -i preview.mp4 -t 40 -map 0:v -c:v libx264 -preset veryfast -crf 26 -g 1 -bf 0 -pix_fmt yuv420p
  -movflags empty_moov+default_base_moof -frag_duration 500000 v_intra.mp4` (해상도는 원래 1280px).
- 소리: `ffmpeg -i 3_clean.mp4 -t 24.4626 -map 0:a -c:a aac -b:a 128k -movflags empty_moov+default_base_moof -frag_duration 500000 a_final.mp4`.
  SourceBuffer 에 `timestampOffset = 0`, appendWindow 없이 처음부터 끝까지 넣었다. 이때 WKWebView 소리 버퍼는 0.000초부터
  시작했다 (B 에서 원본 소리를 구간마다 자를 땐 0.015초부터). priming·edit list 는 따로 다루지 않았다.
- 영상 `appendWindowEnd` 의 +1프레임은 **미리보기 파일의 프레임 간격**(1/30초) 기준이다.
- 남길 구간은 `cuts.json` 의 `start_frame`/`end_frame` 을 원본 fps(`541020/18031`)로 나눈 초 — 렌더(`keep_segments`)와 같은 계산.
- 조각 위치는 브라우저에서 전체 파일을 받아 상자를 읽어 찾았다 (앱에서는 index JSON + Range 로 바꾼다).

### 4. 배경 잡음(`--denoise-level`) 바꾸기

지금은 다시 판정 없이 미리보기 소리만 다시 만든다. 새 방식에서도 미리보기 소리를 다시 만든 뒤 2의 잘린 소리도
다시 만든다 (같은 명령에 포함).

## 빌더에게 맡기는 것

- index JSON 정확한 모양, 해시 방식, 오래된 소리 파일을 몇 개 남길지.
- 버퍼 범위 숫자, 버퍼 관리 코드 구조.
- 재생기 코드를 `app.js` 안에 둘지 별도 파일로 나눌지 (지금은 한 파일).
- 백그라운드 작업 실행 방식 (`jobqueue` 를 쓸지 별도 스레드로 할지). 분석·렌더 중인 같은 영상과 겹칠 때의 처리.

## 확인 방법

- pytest: index 생성(상자 읽기)은 작은 합성 fMP4 로, 잘린 소리 길이는 `cut_audio` 와 같은지(샘플 수 = 결과 영상 프레임 수에
  맞음), 컷 해시·캐시, `get_result` 의 새 필드. ffmpeg 가 필요한 테스트는 CI 에서 건너뛰게 표시한다.
- 앱에서 3.mp4 로: WKWebView 에서 `requestVideoFrameCallback` 간격으로 이음새 멈춤 0 (시험판과 같은 측정), 컷 되살리기 후
  소리·영상이 같이 바뀌는지, 1시간 영상에서 끝까지 재생되는지(버퍼 한도).
- 사용자가 맥·윈도우에서 직접 들어 보고 시험판 E 와 같은지 확인.
